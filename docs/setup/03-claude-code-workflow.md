# Как ведём разработку с Claude Code

Статус: 2026-10-08. Порядок, отработанный на Eventbase за три месяца
(600 PR, 9 приложений, несколько параллельных сессий в день), с
поправками на выученные грабли. Коротко он же — в корневом `CLAUDE.md`,
который сессии читают автоматически; здесь — почему так.

## 1. Единица работы — задача, и у неё одна сессия

- Владелец формулирует задачу словами в Claude Code (веб). Сессия
  создаёт ветку `claude/<тема>-<суффикс>`, работает, открывает PR.
- Задача умещается в один PR и одну папку приложения. Если по ходу
  выясняется, что нужен новый общий тип или таблица — сессия
  **останавливается и говорит об этом**, а не меняет контракт «попутно»:
  общие слои (`packages/shared`, `supabase/migrations`) меняются
  отдельным небольшим PR, который вливается **до** старта зависящих
  задач. Иначе два PR, добавившие по колонке в одну таблицу, конфликтуют
  в миграциях, а третья сессия строит код на контракте, которого в
  `main` ещё нет.
- Ветки короткие: ответвляемся от свежей `main`, вливаемся в конце
  раунда. Ветка, живущая неделями, — будущий разъезд репозитория
  (в Eventbase сведение трёх разошедшихся копий стоило вечера).

## 2. Ритуал начала сессии

```bash
git fetch origin
git log --oneline origin/main -20     # что поменяли соседние сессии
```

Сообщения коммитов пишутся прозой и объясняют «почему» — этого
достаточно, чтобы понять чужую правку без диффа. Пример из Eventbase:
«Админка: вход по ссылке из письма Supabase больше не обходит второй
фактор (#589)».

Потом сессия читает `CLAUDE.md` корня и приложения, в котором работает,
и — если задача касается базы — `docs/architecture/02-data-model.md`.

## 3. Что обязано быть в PR

- Код и миграция **вместе**, если код пишет в новую колонку: PostgREST
  отвечает `PGRST204` на неизвестную колонку, падает вся форма и
  набранный текст теряется (урок 28.08.2026 Eventbase).
- Новая таблица = RLS (четыре политики) + строка в матрице
  `supabase/tests/01-core-rls.sql` + индексы + бакет, если есть файлы.
- Решение шире своей папки — строка в `CLAUDE.md` или ADR тем же коммитом.
- Описание PR: что меняется в схеме (имя файла миграции), что проверено
  (локальная сборка затронутого приложения, тест базы), скриншот для
  видимых правок.
- Номер версии приложения повышен (`lib/version.ts`): иначе «не доехало»
  не отличить от «не сработало».

## 4. Проверки и слияние

- CI на PR: быстрые проверки → тест базы (если затронут `supabase/`) →
  сборка затронутого → браузерные сценарии (если есть). Пропущенная
  задача — «не затронуто», а не «не проверено».
- Перед PR сессия сама гоняет `pnpm --filter portal build` и, при
  правке базы, `bash supabase/tests/run.sh`.
- **Зелёный PR вливается сразу, без вопроса «заливать?»** — решение
  владельца Eventbase (16.08.2026), подтверждённое для этой платформы.
  Сомнение по **сути** задачи задаётся до работы, а не после: разрешение
  на выкат — не разрешение угадывать.
- Слияние в `main` → Coolify собирает образ → новый контейнер накатывает
  миграции → healthcheck → замена. Если выкат упал — сессия, которая
  вливала, разбирается первой (лог сборки в Coolify, GlitchTip).

## 5. Параллельные сессии: распределение

| Сессия | Папка | Пример задачи |
|---|---|---|
| Контракты | `packages/shared`, `supabase/migrations` | «таблицы задач и политики» — вливается первой |
| Портал: база знаний | `apps/portal/src/app/(portal)/kb/` | редактор статей |
| Портал: задачи | `apps/portal/src/app/(portal)/tasks/` | доска клуба |
| Портал: чаты | `apps/portal/src/app/(portal)/chats/` | хвост переписки |
| Площадка | `docs/setup/`, Coolify через браузер | бэкапы, мониторинг |
| Аудит | читает всё, пишет `supabase/tests/NN-audit-*.sql` | «собственник как нападающий» |

Две сессии в одной папке одновременно — конфликт при слиянии; владелец
не ставит такие задачи параллельно либо явно разводит их по подпапкам.

## 6. Runbook'и для браузерного агента

Настройка внешних сервисов (Timeweb, Coolify, Unisender, Telegram) —
тоже задача для сессии, но «в браузере»: документ с шагами, где
🤖 делает агент, а 🔴 — человек (оплата, паспорт, 2FA, пароли).
Образец — `docs/setup/01-timeweb-server.md`. Секреты агент записывает
только в поля Coolify и менеджер паролей — никогда в чат.

## 7. Правила-обереги для сессий (из опыта Eventbase)

- Правила хранятся **в репозитории**, а не в памяти сессии: сессия
  видит файлы, а не прошлые диалоги.
- `CLAUDE.md` — закон, но с бюджетом размера. В Eventbase файл правил
  приложения вырос до 762 КБ и перестал помещаться в контекст; здесь
  корневой ≤ 40 КБ, приложения ≤ 60 КБ, темы — в `docs/patterns/`, и
  `scripts/check-doc-size.mjs` падает при превышении.
- Решения владельца записываются с датой («решение владельца
  12.09.2026») — так следующая сессия отличает правило от предположения.
- Имя снаружи и имя в коде — разные вещи: подписи переименовываются
  свободно, идентификаторы, таблицы и папки — никогда без явного запроса.
- Отчёт о работе — по-русски, включая заголовки и подписи к спискам.

## 8. Чего не делаем

- Не применяем миграции руками (кроме разрушающих — с бэкапом и
  отметкой в журнале).
- Не держим адреса, ключи, домены в коде.
- Не пишем `if (окружение)`: один образ на все окружения, различия —
  в переменных.
- Не вводим новую службу (Redis, Realtime, очередь) без ADR.
- Не правим применённую миграцию — только новый файл.
- Не спрашиваем «заливать?» у готовой задачи.
