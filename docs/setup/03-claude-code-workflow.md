# Как ведём разработку с Claude Code

Статус: 2026-10-08. Коротко — в корневом `CLAUDE.md`, который сессии
читают автоматически; здесь — почему так.

## 1. Единица работы — задача, у неё одна сессия

- Владелец формулирует задачу в Claude Code (веб). Сессия создаёт ветку
  `claude/<тема>-<суффикс>`, работает, открывает PR.
- Задача умещается в один PR и одну папку приложения. Если нужен новый
  общий тип или таблица — сессия **останавливается и говорит об этом**:
  общие слои (`packages/shared`, `supabase/migrations`) меняются
  отдельным PR, который вливается **до** зависящих задач. Иначе два PR с
  колонкой в одну таблицу конфликтуют в миграциях, а третья сессия
  строит код на контракте, которого в `main` нет.
- Ветки короткие: от свежей `main`, обратно в конце раунда.

## 2. Ритуал начала сессии

```bash
git fetch origin
git log --oneline origin/main -20     # что поменяли соседние сессии
```

Сообщения коммитов — прозой, с «почему»: по ним понятна чужая правка
без диффа. Затем — `CLAUDE.md` корня и приложения, а при работе с базой
— `docs/architecture/03-data-model.md`.

## 3. Что обязано быть в PR

- Код и миграция **вместе**, если код пишет в новую колонку.
- Новая таблица = четыре политики + строка в матрице теста + индексы +
  бакет, если есть файлы.
- Решение шире своей папки — строка в `CLAUDE.md` или ADR тем же
  коммитом.
- Описание PR: что меняется в схеме (имя миграции), что проверено
  (сборка затронутого, тест базы), скриншот для видимых правок.
- Номер версии приложения повышен.

## 4. Проверки и слияние

- CI на PR: быстрые проверки → тест базы (если затронут `supabase/`) →
  сборка затронутого → браузерные сценарии. Пропущенная задача — «не
  затронуто».
- Перед PR сессия сама гоняет `pnpm --filter portal build` и, при правке
  базы, `bash supabase/tests/run.sh`.
- **Зелёный PR вливается сразу, без вопроса «заливать?»** — решение
  владельца. Сомнение по **сути** задачи задаётся до работы, а не после.
- Слияние → Coolify собирает образ → новый контейнер накатывает миграции
  → healthcheck → замена. Упал выкат — разбирается сессия, которая
  вливала.

## 5. Параллельные сессии

| Сессия | Папка | Пример |
|---|---|---|
| Контракты | `packages/shared`, `supabase/migrations` | таблицы задач и политики — вливается первой |
| База знаний | `apps/portal/src/app/(portal)/kb/` | редактор статей |
| Задачи | `apps/portal/src/app/(portal)/tasks/` | доска клуба |
| Чаты | `apps/portal/src/app/(portal)/chats/` | хвост переписки |
| Площадка | `docs/setup/`, Coolify через браузер | бэкапы, мониторинг |
| Аудит | читает всё, пишет `supabase/tests/NN-audit-*.sql` | «собственник как нападающий» |

Две сессии в одной папке одновременно — конфликт при слиянии; такие
задачи не ставятся параллельно либо разводятся по подпапкам.

## 6. Runbook'и для браузерного агента

Настройка внешних сервисов — тоже задача для сессии «в браузере»:
документ с шагами, где 🤖 делает агент, 🔴 — человек. Образец —
`docs/setup/01-timeweb-server.md`. Секреты агент записывает только в
Coolify и менеджер паролей.

## 7. Правила-обереги

- Правила живут **в репозитории**: сессия видит файлы, а не прошлые
  диалоги.
- `CLAUDE.md` — закон, с бюджетом размера (корневой ≤ 40 КБ, приложения
  ≤ 60 КБ); темы — в `docs/patterns/`; `check-doc-size.mjs` в CI.
- Решения владельца записываются с датой — так следующая сессия отличает
  правило от предположения.
- Имя снаружи и имя в коде — разные вещи.
- Отчёт о работе — по-русски, включая заголовки и подписи.

## 8. Чего не делаем

- Не применяем миграции руками (кроме разрушающих).
- Не держим адреса, ключи, домены в коде; не пишем `if (окружение)`.
- Не вводим новую службу без ADR.
- Не правим применённую миграцию.
- Не спрашиваем «заливать?» у готовой задачи.
