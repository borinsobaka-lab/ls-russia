# ADR platform-002: вход сотрудников со вторым фактором

Статус: предложено — 2026-10-08

## Контекст

300–400 сотрудников УК и собственников студий, у которых в руках будут
данные клиентов сети. Требование владельца: второй фактор обязателен.
Пользователи — не ИТ-специалисты (собственники 35–50 лет, администраторы
на ресепшене). Почта — не корпоративная у половины. Сессия должна жить
неделями на личном телефоне и гаснуть мгновенно при увольнении.

Опыт Eventbase: админка входит по паролю, затем обязательный 6-значный
код из письма (своя таблица, трюк `generateLink + verifyOtp` для выдачи
сессии, потому что серверный `signInWithPassword` сразу пишет куки).
Минусы, которые проявились: письмо стоит на критическом пути каждого
входа (Resend за Cloudflare — код приходил через раз, пока не перешли на
Unisender); код из письма нельзя проверить в политиках базы; ссылка из
письма Supabase однажды обошла второй фактор (#589).

## Варианты

1. **Пароль + код из письма** (как в Eventbase). Проверенный модуль,
   переносится за день. Но зависимость входа от почты и невозможность
   доказать второй фактор базе остаются.
2. **Пароль + TOTP через GoTrue MFA** (выбрано). Встроено в self-hosted
   Supabase, включено по умолчанию, даёт `aal2` в JWT, который читает
   RLS. Приложение-аутентификатор (Яндекс Ключ, Google Authenticator)
   работает без сети и без SMS. Минус — порог для нетехнических
   пользователей; снимается инструкцией с картинками при первом входе и
   поддержкой УК.
3. **Пароль + SMS-код через GoTrue phone MFA** с хуком отправки на
   российский шлюз. Удобнее TOTP, но 3–5 ₽ за вход и зависимость от
   шлюза. Оставлен как **дополнительный фактор** для тех, кому TOTP не
   даётся — добавляется тем же механизмом, тоже даёт `aal2`.
4. Вход по телефону без пароля (как у клиентов). Отклонено для
   сотрудников: один фактор.

## Решение

- GoTrue: почта + пароль (`PASSWORD_MIN_LENGTH=12`), `DISABLE_SIGNUP=true`,
  учётки создаются админ-API с `email_confirm: true` по приглашению,
  письмо приглашения шлёт платформа своим шаблоном (Unisender Go), а не
  GoTrue.
- **TOTP обязателен для всех.** Первый вход: пароль из приглашения →
  экран регистрации фактора (QR + ручной код + инструкция) → проверка
  → смена пароля → портал. Пока фактор не зарегистрирован,
  `profiles.mfa_enrolled_at` пуст и middleware пускает только на `/mfa`.
- **В базе личность = `aal2`**: `app.staff_id()` возвращает `auth.uid()`
  только при клейме `aal = 'aal2'` и активной учётке. Сессия после
  пароля, но до TOTP (`aal1`) не видит ни одной строки — это проверяет
  тест, а не middleware.
- Доверенное устройство: `aal2` живёт в сессии GoTrue; refresh-токены
  ротируются, access-токен час. Второй фактор спрашивается при новом
  входе (новое устройство, выход, истёкший refresh), не каждый день.
- Восстановление: потерял телефон → сотрудник УК с правом
  `people.manage` (или супер-админ) сверяет личность голосом и
  сбрасывает фактор через админ-API GoTrue; событие — в `audit_log`;
  пользователю уходит письмо «ваш второй фактор сброшен». Резервных
  кодов не делаем: их теряют вместе с телефоном, а поддержка УК рядом.
- Сброс пароля: собственные токены (`sha256`, 60 минут), ссылка только
  из `PORTAL_PUBLIC_URL`; маршрут `/auth/confirm` сессию не выдаёт.
- Блокировка (`profiles.status = 'blocked'`) и выход гасят доступ
  немедленно: `app.staff_id()` смотрит статус на каждом запросе.
- Лимиты входа — в базе (`auth_rate_events`): пароли 10/15 мин на почту,
  25/15 мин на IP; TOTP 6/10 мин; сброс 5/час; троттл, не вечная
  блокировка.

## Последствия

- Поддержка объясняет TOTP; в базу знаний первой ложится статья «Как
  войти в портал» со скриншотами для iPhone и Android.
- `aal2` в JWT — единственный способ дать RLS знание о втором факторе;
  поэтому любой другой второй фактор (SMS, позже — ключи доступа
  passkeys, если GoTrue их получит) добавляется через GoTrue, а не
  своей таблицей.
- Клиенты (релиз 3) входят иначе (телефон + код, свои сессии) и в этот
  ADR не входят.
