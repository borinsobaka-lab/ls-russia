# ADR platform-002: вход сотрудников со вторым фактором

Статус: предложено — 2026-10-08

## Контекст

300–400 сотрудников УК и собственников, у которых в руках будут данные
клиентов сети. Второй фактор обязателен (требование владельца).
Пользователи — не ИТ-специалисты; почта у половины личная. Сессия
должна жить неделями на телефоне и гаснуть мгновенно при увольнении.

## Варианты

1. **Пароль + одноразовый код из письма** (своя таблица кодов). Понятно
   пользователю, но письмо стоит на критическом пути каждого входа
   (сбой почты = никто не входит), а второй фактор не виден базе:
   политики RLS не могут отличить сессию «после кода» от сессии «до».
2. **Пароль + TOTP через GoTrue MFA** (выбрано). Встроено в self-hosted
   Supabase, включено по умолчанию; после проверки фактора JWT получает
   клейм `aal = aal2`, который читает RLS. Приложение-аутентификатор
   (Яндекс Ключ, Google Authenticator) работает без сети и SMS. Минус —
   порог для нетехнических пользователей; снимается инструкцией с
   картинками при первом входе и поддержкой УК.
3. **Пароль + SMS-код через GoTrue phone MFA** с хуком отправки на
   российский шлюз. Мягче порог, но 3–5 ₽ за вход и зависимость от шлюза.
   Оставлен как **дополнительный фактор** для тех, кому TOTP не даётся —
   тем же механизмом, тоже даёт `aal2`.
4. Вход по телефону без пароля. Отклонено для сотрудников: один фактор.

## Решение

- GoTrue: почта + пароль (`PASSWORD_MIN_LENGTH=12`), `DISABLE_SIGNUP=true`;
  учётки создаёт админ-API с `email_confirm: true` по приглашению; письмо
  приглашения шлёт платформа своим шаблоном.
- **TOTP обязателен для всех.** Первый вход: пароль из приглашения →
  регистрация фактора (QR, ручной код, инструкция) → проверка → смена
  пароля → портал. Пока `profiles.mfa_enrolled_at` пуст, middleware
  пускает только на `/mfa`.
- **В базе личность = `aal2`**: `app.staff_id()` возвращает `auth.uid()`
  только при клейме `aal = 'aal2'` и активной учётке. Сессия `aal1` не
  видит ни одной строки — проверяет тест, а не middleware.
- Доверенное устройство: `aal2` живёт в сессии GoTrue; refresh-токены
  ротируются, access-токен час; второй фактор спрашивается при новом
  входе, не каждый день.
- Восстановление: потерял телефон → сотрудник с правом `people.manage`
  сверяет личность голосом и сбрасывает фактор через админ-API;
  событие — в `audit_log`; пользователю — письмо «ваш второй фактор
  сброшен». Резервных кодов не делаем: их теряют вместе с телефоном, а
  поддержка УК рядом.
- Сброс пароля — собственные токены (`sha256`, 60 минут), ссылка только
  из `PORTAL_PUBLIC_URL`; маршрут подтверждения из письма сессию не
  выдаёт.
- Блокировка (`profiles.status = 'blocked'`) и выход гасят доступ
  немедленно: `app.staff_id()` смотрит статус на каждом запросе.
- Лимиты входа — в базе (`auth_rate_events`): пароли 10/15 мин на почту,
  25/15 мин на IP; TOTP 6/10 мин; сброс 5/час; троттл, не блокировка.

## Последствия

- Первая статья базы знаний — «Как войти в портал» со скриншотами для
  iPhone и Android.
- Любой другой второй фактор (SMS, позже passkeys) добавляется через
  GoTrue, а не своей таблицей: только так RLS узнаёт о нём.
- Клиенты (релиз 3) входят иначе (телефон + код, свои сессии) и в этот
  ADR не входят.
