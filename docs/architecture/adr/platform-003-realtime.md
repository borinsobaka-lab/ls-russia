# ADR platform-003: живые обновления (чаты, задачи, уведомления)

Статус: предложено — 2026-10-08

## Контекст

Мессенджер и задачи требуют «появилось само» для 300–400 одновременных
пользователей, в перспективе — тысячи клиентов в приложении. Приём
данных — обычный POST (идемпотентный по `client_key`); раздача —
однонаправленная.

## Варианты

1. **Supabase Realtime** (подписка на изменения таблиц). Ещё один
   сервис (Elixir) в compose, свои лимиты соединений; изменения приходят
   строками без учёта того, что видно подписчику, — фильтрация всё равно
   на нашем сервере.
2. **WebSocket на сервере приложения.** Двусторонний канал не нужен;
   WS требует кастомного сервера Next или отдельного процесса.
3. **SSE + откат на опрос, комната-снимок в процессе** (выбрано). Один
   `EventSource` на вкладку (`/api/live`); в процессе — одна «комната» на
   сеть: раз в секунду снимок свежайших строк (последние сообщения,
   изменённые задачи, новые уведомления) сравнивается с предыдущим,
   разница рассылается подписчикам **уже отфильтрованной по членству**.
   Реплики не общаются между собой — общая точка Postgres. Стоимость —
   несколько маленьких запросов в секунду на сеть независимо от числа
   подключённых. Снимок, а не курсор по времени: курсор теряет строки,
   чья транзакция записала время раньше, чем закоммитилась, и не видит
   удалений.
4. `LISTEN/NOTIFY` из триггеров. Мгновенно, но требует прямого
   соединения с Postgres из приложения (сейчас всё через PostgREST) и
   обработки потерь при обрыве. Оставлен как оптимизация после варианта
   3, если тик в секунду станет заметен.

## Решение

Вариант 3:

- первая строка ответа `retry:` со случайной паузой 2–20 с (размазать
  переподключения после выката); событие `hello {build}` — вкладка со
  старой сборкой перезагружается, когда видна и человек не печатает;
  пинг каждые 15 с; `X-Accel-Buffering: no`;
- нет слота — событие `fallback` кодом 200; клиент уходит на опрос
  25±10 с и пробует SSE снова с удвоением паузы от 30 с до 5 мин;
- тик 1 с, флаг `busy` (тики не наслаиваются); снимок читается токеном
  уровня сети без личности; личные переписки — через функцию «id, время,
  состав — без содержимого»;
- клиент по умолчанию — `router.refresh()` (одна правда на сервере);
  открытая переписка дописывает хвост `api/chat/<id>/tail?after=<lastId>`
  без перерисовки; при хвосте длиннее 150 или ответе `reset` — полная
  перечитка;
- ярлыки непрочитанного — склейка 1 с, один запрос в полёте, только на
  видимой вкладке;
- пределы: 4 соединения на пользователя, `LIVE_SSE_MAX` на процесс.

«Печатает…» и «в сети» — эфемерные состояния комнаты; присутствие
пишется в `user_presence` раз в 2 минуты и показывается точкой.

## Последствия

- Задержка до секунды — для корпоративного мессенджера незаметна.
- Горизонтальный рост — добавить реплику; ведро лимитов в памяти делится
  на `APP_REPLICAS`.
- Выкат рвёт все SSE разом — вкладки переподключаются с разбросом.
- Переход на `LISTEN/NOTIFY` или Realtime — новым ADR, не «попутно».
