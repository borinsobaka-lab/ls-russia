# План платформы Lady Stretch: что строим, на чём и в каком порядке

Статус: предложено владельцу — 2026-10-08. Входной документ: отвечает
«что, на чём и зачем», детали — в соседних файлах. После одобрения
статус меняется на «принято», дальше правки — только через PR.

## 1. Что строим

Единая платформа диджитал-продуктов сети студий растяжки: один
репозиторий, одна база, один сайт для сотрудников и собственников, одно
приложение для клиентов.

| Продукт | Для кого | Релиз |
|---|---|---|
| **База знаний** — регламенты, стандарты, обучение; редактирование в браузере, версии, доступ по ролям, подтверждение «ознакомлен» | собственники студий, управляющая компания (УК) | 1 |
| **Задачи** — доски УК и клубов, поручения всей сети с контролем выполнения, чек-листы, повторяющиеся задачи | УК ↔ собственники, персонал клубов | 1 |
| **Чаты** — личные, группы, каналы объявлений, чат клуба с УК, обсуждения задач; живые обновления, файлы, поиск | те же | 1 |
| **Портал как PWA** с уведомлениями на телефон и почту; вход по паролю со вторым фактором | те же | 1 |
| Отчёты по сети, Telegram-уведомления, шаблоны, экспорт | УК | 2 |
| **Клиентское приложение** (PWA, затем сборки в магазины): расписание, запись, абонементы, оплата | клиенты студий | 3 |
| **Кабинет клуба**: клиенты, абонементы, расписание, CRM, единое окно переписки с клиентами (Telegram, MAX, VK), права по сотрудникам | собственники, управляющие, администраторы, тренеры | 4 |

Релизы 1–2 — костяк, заменяющий Битрикс; 3–4 строятся на том же ядре
и не требуют его переделки. Подробно — `04-products.md`.

## 2. На чём строим

Коротко: **один язык — TypeScript — на всех слоях, кроме базы; в базе —
SQL и PL/pgSQL.** Фронтенд и сервер — Next.js на React; база, вход и
файлы — Supabase на своём сервере; выкат — Coolify на сервере Timeweb
Cloud в Москве. Полный перечень языков, фреймворков, библиотек и причин
— `01-tech-stack.md`; сервисы, сервер, сеть и стоимость —
`02-infrastructure.md`.

Стек и подход проверены на предыдущей платформе владельца; код новой
платформы пишется с нуля.

Шесть решений, определяющих всё остальное (каждое — ADR в `adr/`):

1. **Изоляция данных живёт в базе (RLS), не в коде.** Сеть → клубы →
   люди; права считают функции схемы `app`; у каждого «мира»
   (сотрудники, клиенты, интеграции) своё пространство имён клеймов —
   `platform-001`, `03-data-model.md`.
2. **Второй фактор — TOTP через GoTrue, и база его видит** (`aal2` в
   JWT): сессия без второго фактора не читает ни одной строки —
   `platform-002`.
3. **Живые обновления — SSE с комнатой-снимком** в процессе
   приложения, без Supabase Realtime, Redis и WebSocket — `platform-003`.
4. **Уведомления — четыре слоя** (лента в портале, push, письмо,
   Telegram), источник правды один, доставка воркером — `platform-004`.
5. **Статьи — JSON-документ редактора в базе** с версиями, аудиторией и
   полнотекстовым поиском на русском — `platform-005`.
6. **Всё выкатывается само**: push в `main` → Coolify собирает образ →
   новый контейнер накатывает миграции при старте → healthcheck → замена
   старого. Человек не применяет миграции руками, кроме разрушающих.

## 3. Порядок работ

### Этап 0 — площадка и репозиторий (неделя 1)

- 🔴 Владелец: аккаунт Timeweb, домен, баланс, Unisender, Telegram-группа
  тревог, решения из § 6.
- 🤖 Сервер по `docs/setup/01-timeweb-server.md`: Coolify, Supabase,
  S3, бэкапы, мониторинг. Готово = Auth отвечает по `api.<домен>`,
  бэкап лежит в S3, восстановление проверено.
- 🤖 Репозиторий по `docs/setup/02-repo-bootstrap.md`: монорепо,
  `apps/portal` с каркасом и `/api/health`, `packages/shared`,
  `supabase/` с применением миграций, стендом и первой миграцией ядра,
  CI. Готово = push в `main` выкатывает «Портал, версия 1».

### Этап 1 — ядро (недели 2–3)

Вход (пароль + TOTP, приглашения, сброс, блокировка), профили, сеть и
клубы, членства и роли, журнал действий, лента уведомлений, очередь
фоновых задач и воркер с пульсом, реестр файлов и загрузки, каркас
портала (меню, карточка человека, формы, окна, таблицы), ошибки в
GlitchTip. Матрица видимости в тесте. Готово = админ УК завёл клуб и
пригласил собственника, тот вошёл с TOTP с телефона и видит только
свой клуб.

### Этап 2 — база знаний (недели 3–6)

Разделы, статьи, редактор, версии, аудитория, «ознакомлен» с отчётом,
поиск, файлы, установка PWA. Готово = УК опубликовала 10 реальных
регламентов, 20 собственников подтвердили ознакомление, поиск находит
по морфологии.

### Этап 3 — задачи (недели 5–9)

Доски, задачи, комментарии, чек-листы, вложения, «Мои задачи»,
поручение сети со сводкой, повторяющиеся задачи, уведомления о
назначении и сроках, письма при непрочтении. Готово = УК поставила
поручение всем клубам и видит «сделано N из M», просроченные получают
напоминание сами.

### Этап 4 — чаты (недели 7–11)

Личные, группы, каналы, чат клуба, обсуждение задачи; SSE-канал,
хвост переписки, маркеры прочтения, вложения, поиск, push, письмо при
непрочтении, модерация. Готово = 20 собственников-пилотов месяц
переписываются с УК здесь.

### Этап 5 — пилот и раскатка (недели 11–14)

Пилот 20 клубов → разбор → аудит «собственник как нападающий» →
исправления → раскатка волнами по 50 клубов. Параллельно — релиз 2.

Этапы перекрываются: сессии Claude Code работают параллельно в своих
папках. Сроки — ориентир; реальный темп покажет этап 1.

### Этапы 6+ — клиентское приложение и кабинет клуба

Отдельный план после пилота. Ядро к ним готово: клиенты принадлежат
сети, их клеймы в своём пространстве имён, файлы приватные,
уведомления многоканальные, платёжные шлюзы выбраны.

## 4. Как мы работаем

Задача = ветка = сессия Claude Code = PR в `main`. Одна задача — одна
папка приложения; общие контракты (`packages/shared`,
`supabase/migrations`) меняются отдельным PR **до** зависящих задач.
Миграции только добавляются и едут тем же PR, что и код. PR проходит
CI и сливается сразу, без вопроса «заливать?». Решение шире своей папки
записывается в `CLAUDE.md` или ADR тем же коммитом. Подробно —
`docs/setup/03-claude-code-workflow.md` и корневой `CLAUDE.md`.

## 5. Сервер: минимум на старте и рост

Один сервер Timeweb Cloud 4 vCPU / 8 ГБ / 80 ГБ NVMe (Москва) + S3 +
домен: **~2–4 тыс. ₽/мес** на всё, включая мониторинг. Меньше нельзя:
стек Supabase и пик сборки Next.js не помещаются в 4 ГБ. Рост —
вторым сервером под наблюдение, затем базой на отдельном сервере к
клиентскому приложению, затем репликами приложений за балансировщиком.
Подробно — `02-infrastructure.md`.

## 6. Решения, которые нужны от владельца до этапа 0

1. **Домен** и внешние названия портала и клиентского приложения
   (в коде — `portal` и `client`, это не меняется).
2. **Второй фактор**: TOTP для всех с первого дня (рекомендация) или
   TOTP для УК и SMS-код для собственников (дороже, мягче порог).
3. **Оператор персональных данных** — УК сети; разработчик —
   обработчик по договору поручения. Кто подаёт уведомление в РКН.
4. **Пилотная группа**: 20 собственников и 3–5 сотрудников УК.
5. **Telegram-бот уведомлений** — в релиз 1 или 2.
6. **Что переносить из Битрикса**: людей и структуру или ещё задачи и
   файлы (отдельная задача импорта).

Ответы записываются сюда под заголовком «Решения владельца» с датой.
