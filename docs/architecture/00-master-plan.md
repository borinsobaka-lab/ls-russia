# План платформы Lady Stretch: что строим, из чего и в каком порядке

Статус: предложено владельцу — 2026-10-08. Это входной документ: он
отвечает «что и зачем», а детали разложены по соседним файлам, на
которые он ссылается. После одобрения владельцем статус меняется на
«принято», и дальше правится только через PR.

## 1. Что строим

Единая платформа диджитал-продуктов для сети студий растяжки:

| Продукт | Для кого | Релиз |
|---|---|---|
| **База знаний** — регламенты, стандарты, обучение; редактирование в браузере, версии, доступ по ролям, подтверждение «ознакомлен» | собственники студий, УК | 1 |
| **Задачи** — доски УК и клубов, поручения всей сети с контролем выполнения, чек-листы, повторяющиеся задачи | УК ↔ собственники, персонал клубов | 1 |
| **Чаты** — личные, группы, каналы объявлений, чат клуба с УК, обсуждения задач; живые обновления, файлы, поиск | те же | 1 |
| **Портал как PWA** с уведомлениями на телефон и почту, вход по паролю со вторым фактором | те же | 1 |
| Отчёты по сети, Telegram-уведомления, шаблоны и экспорт | УК | 2 |
| **Клиентское приложение** (PWA → сборки в магазины): расписание, запись, абонементы, оплата | клиенты студий | 3 |
| **Кабинет клуба**: клиенты, абонементы, расписание, CRM вместо amoCRM, единое окно переписки с клиентами (Telegram, MAX, VK), права по сотрудникам | собственники, управляющие, администраторы, тренеры | 4 |

Всё — один репозиторий, одна база, один сайт для сотрудников
(`office.<домен>`) и одно приложение для клиентов (`app.<домен>`).
Релизы 1–2 — «костяк», который заменяет Битрикс; 3–4 строятся на том же
ядре. Подробно — `03-products.md`.

## 2. Из чего (стек и почему он такой)

Стек — тот же, что у Eventbase, потому что оттуда переносятся не идеи, а
файлы: Next.js 15 + React 19 + TypeScript + Tailwind 4 в pnpm-монорепо;
Supabase на своём сервере (Postgres + GoTrue + PostgREST + Storage);
Coolify на сервере Timeweb Cloud в Москве; Timeweb S3 для файлов и
бэкапов; Unisender Go для почты; GlitchTip + Uptime Kuma для
наблюдения; GitHub Actions для проверок на PR. Таблица со всеми
слоями и обоснованиями — `01-infrastructure.md`.

Шесть архитектурных решений, которые определяют всё остальное
(каждое — свой ADR в `adr/`):

1. **Изоляция данных живёт в базе (RLS), не в коде.** Сеть → клубы →
   люди; права считают функции `app.*`; у каждого «мира» (сотрудники,
   клиенты, интеграции) своё пространство имён клеймов. —
   `platform-001`, `02-data-model.md`.
2. **Второй фактор — TOTP через GoTrue, и база его видит** (`aal2` в
   JWT): сессия без второго фактора не читает ни одной строки. —
   `platform-002`.
3. **Живые обновления — SSE с комнатой-снимком**, без Supabase Realtime,
   Redis и WebSocket. — `platform-003`.
4. **Уведомления — четыре слоя** (лента в портале, push, письмо,
   Telegram), источник правды один, доставка воркером. — `platform-004`.
5. **Статьи — JSON-документ редактора в базе** с версиями, аудиторией и
   поиском на `russian`. — `platform-005`.
6. **Всё выкатывается само**: push в `main` → Coolify собирает образ →
   новый контейнер накатывает миграции при старте → проходит healthcheck
   → заменяет старый. Человек не применяет миграции руками никогда,
   кроме разрушающих.

## 3. Что берём из Eventbase

Короткий ответ: **механику целиком, предметную область — нет.**
Переносятся файлами: скрипт миграций и журнал, тестовый стенд базы с
матрицей ролей, проверка контракта «код ↔ схема», CI по затронутому,
Dockerfile'ы, клиенты Supabase и проверки прав, `mustWrite` и классы
ошибок, лимиты в базе, журнал действий, заголовки безопасности, очередь
`jobs` с воркером, Web Push, SSE-канал, service worker с проверкой в CI,
загрузки прямо в Storage, пережатие картинок, GlitchTip без
персональных данных, модули платежей. Не переносятся: два контура,
копирование проектов, расширения, голосования и всё событийное.
Меняются: второй фактор (TOTP вместо кода из письма), момент применения
миграций (entrypoint вместо pre-deploy), чаты (явное членство, правка и
удаление, маркеры прочтения), размер правил для сессий. Полный список
с путями и 35 «граблями», превращёнными в правила, —
`05-eventbase-lessons.md`.

## 4. Порядок работ

### Этап 0 — площадка и репозиторий (неделя 1)

- 🔴 Владелец: аккаунт Timeweb, домен, баланс, Unisender, Telegram-группа
  тревог, решения из § 7.
- 🤖 Сервер по `docs/setup/01-timeweb-server.md`: Coolify, Supabase,
  S3, бэкапы, Kuma. Итог — `https://api.<домен>/auth/v1/health` отвечает,
  бэкап лежит в S3, восстановление проверено.
- 🤖 Репозиторий по `docs/setup/02-repo-bootstrap.md`: монорепо,
  `apps/portal` с пустым каркасом и `/api/health`, `packages/shared`,
  `supabase/` с `apply.sh`, стендом и первой миграцией ядра, CI. Итог —
  push в `main` выкатывает «Портал. Версия 1» на `office.<домен>`.

### Этап 1 — ядро (недели 2–3)

Вход (пароль + TOTP, приглашения, сброс, блокировка), профили, сеть и
клубы, членства и роли, журнал действий, лента уведомлений, очередь
`jobs` и воркер с пульсом, реестр файлов и загрузки, каркас портала
(левое меню, карточка человека, формы, окна, таблицы — компоненты из
админки Eventbase), `/api/health`, GlitchTip. Матрица видимости в тесте.
Готово = админ УК завёл клуб и пригласил собственника, тот вошёл с TOTP
с телефона и видит только свой клуб.

### Этап 2 — база знаний (недели 3–6)

Разделы, статьи, редактор, версии, аудитория, «ознакомлен» с отчётом,
поиск, файлы, установка PWA. Готово = УК опубликовала 10 реальных
регламентов, 20 собственников подтвердили ознакомление, поиск находит
по морфологии.

### Этап 3 — задачи (недели 5–9)

Доски, задачи, комментарии, чек-листы, вложения, «Мои задачи»,
поручение сети с сводкой, повторяющиеся задачи, уведомления о
назначении и сроках, письма через 10 минут. Готово = УК поставила
поручение всем клубам и видит «сделано N из M», просроченные получают
напоминание сами.

### Этап 4 — чаты (недели 7–11)

Личные, группы, каналы, чат клуба, обсуждение задачи; SSE-канал,
хвост переписки, маркеры прочтения, вложения, поиск, push, письмо
через 10 минут, модерация. Готово = 20 собственников-пилотов месяц
переписываются с УК здесь, а не в Битриксе и WhatsApp.

### Этап 5 — пилот и раскатка (недели 11–14)

Пилот 20 клубов → разбор → аудит «собственник как нападающий» →
исправления → раскатка на сеть волнами по 50 клубов. Параллельно —
релиз 2 (Telegram-бот, отчёты, шаблоны).

Этапы перекрываются: сессии Claude Code работают параллельно в своих
папках (правила — корневой `CLAUDE.md`). Сроки — ориентир при темпе
Eventbase (новый продукт за 2–3 недели); реальный темп покажет этап 1.

### Этапы 6+ — клиентское приложение и кабинет клуба

Отдельный план после пилота. Ядро к ним готово: клиенты принадлежат
сети, клеймы клиентов в своём пространстве, файлы приватные,
уведомления многоканальные, платёжные модули лежат в Eventbase.

## 5. Как мы работаем (кратко; подробно — `docs/setup/03-claude-code-workflow.md`)

- Задача = ветка = сессия Claude Code в вебе = PR в `main`. Сессия
  начинает с `git fetch` и чтения свежих коммитов `main`.
- Одна задача — одна папка приложения; общие контракты
  (`packages/shared`, `supabase/migrations`) меняются отдельным PR
  **до** зависящих задач.
- Миграции только добавляются и едут тем же PR, что и код; каждая
  таблица получает RLS, строку в матрице теста и индекс.
- PR проходит CI (быстрые проверки, RLS-тест, сборка затронутого) и
  сливается **сразу, без вопроса «заливать?»** — решение владельца из
  Eventbase действует и здесь. Выкат — сам.
- Решение, касающееся не только своей папки, записывается в `CLAUDE.md`
  или ADR тем же коммитом: сказанное только в чате для других сессий не
  существует.
- Отчёт владельцу — по-русски, прозой, с «почему».

## 6. Сервер: минимум на старте и рост

Один сервер Timeweb Cloud 4 vCPU / 8 ГБ / 80 ГБ NVMe (Москва, ~1 100–
1 800 ₽/мес) + S3 + домен: **~2–4 тыс. ₽/мес** на всё, включая
мониторинг. Меньше нельзя: стек Supabase и пик сборки Next.js не
помещаются в 4 ГБ. Рост — вторым сервером под наблюдение, затем базой
на отдельном сервере к клиентскому приложению, затем репликами
приложений за балансировщиком; к релизу 4 ориентир 8–15 тыс. ₽/мес.
Подробно — `01-infrastructure.md` § 3, 7.

## 7. Решения, которые нужны от владельца до этапа 0

1. **Домен** и внешние названия: портал («Кабинет»? «Офис»?),
   клиентское приложение. В коде — `portal` и `client`, это не меняется.
2. **Второй фактор**: TOTP для всех с первого дня (рекомендация) или
   TOTP для УК и SMS-код для собственников (дороже, мягче порог).
3. **Оператор персональных данных** — УК сети; разработчик — обработчик
   по договору поручения. Кто подаёт уведомление в РКН и когда.
4. **Пилотная группа**: 20 собственников и 3–5 сотрудников УК, готовых
   месяц жить в портале и писать замечания.
5. **Telegram-бот уведомлений** — в релиз 1 или 2.
6. **Что мигрировать из Битрикса**: только людей и структуру (дёшево)
   или ещё задачи и файлы (отдельная задача импорта).

Ответы записываются в этот документ под заголовком «Решения владельца»
с датой — так же, как в `CLAUDE.md` Eventbase.
