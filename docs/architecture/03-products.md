# Линейка продуктов и порядок релизов

Статус: предложено — 2026-10-08. Названия продуктов снаружи — решение
владельца; в коде используются английские идентификаторы (`kb`, `tasks`,
`chat`, `clients`, `crm`), и расхождение имени снаружи и имени в коде —
намеренное (урок Eventbase: «Регистрация на площадке» в коде `checkin`,
переименование папок и таблиц стоит смены DNS и миграции по живым
данным, переименование подписей — ничего).

## 0. Общая рамка: один портал, продукты — разделы

Один веб-сервис `apps/portal` (`office.<домен>`), один вход, одна левая
навигация. Продукт — раздел с собственными таблицами и своей папкой
`apps/portal/src/app/(portal)/<продукт>/`. Клиентское приложение
(`apps/client`, `app.<домен>`) — отдельный мир с отдельной
аутентификацией и своей PWA-областью (ADR event-app-002 Eventbase: у двух
аудиторий разные домены, манифесты и service worker'ы).

Порядок релизов:

| Релиз | Продукты | Для кого | Готово, когда |
|---|---|---|---|
| **1** | Ядро (вход, люди, клубы, роли, уведомления, файлы) + **База знаний** + **Задачи** + **Чаты** + PWA портала | УК и собственники, 300–400 человек | 20 собственников-пилотов месяц живут без Битрикса; потом вся сеть |
| **2** | Отчёты и дашборды по сети, массовые поручения с контролем, интеграция уведомлений с Telegram, расширения под запросы УК | те же | закрыты запросы пилота |
| **3** | **Клиентское приложение** (PWA): расписание, запись, абонементы, оплата, профиль | клиенты студий | пилот в 3–5 клубах |
| **4** | **Кабинет клуба**: клиенты и абонементы, расписание и загрузка залов, CRM (воронка лидов вместо amoCRM), **единое окно переписки с клиентами** (Telegram, MAX, VK, звонки), права по сотрудникам | собственники и персонал клубов | клубы ведут клиентов здесь, а не в amoCRM/таблицах |

Релизы 3 и 4 идут параллельно после 2: приложение без кабинета клуба
бессмысленно (кто подтвердит запись?), кабинет без приложения — CRM без
клиентов. Ядро релиза 1 заранее знает о них: клиенты принадлежат сети,
клеймы клиентов живут в своём пространстве имён, файлы приватные,
уведомления многоканальные.

## 1. База знаний (`kb`)

Что было в Eventbase (`apps/docs`): статический Next.js, 87 markdown-файлов
в репозитории, навигация из манифеста, поиск по подстроке на клиенте,
без входа и без редактирования. Удобное чтение (три колонки, оглавление,
стрелки «назад/дальше», лента экранов) — **берём**; устройство
«контент = файлы в git» — **не берём**: собственникам нужны редактор,
черновики, история, доступ по ролям и отметка «ознакомлен».

### Что умеет

- **Разделы и дерево статей**: разделы (`kb_spaces`: «Открытие студии»,
  «Стандарты сервиса», «Маркетинг», «Обучение тренеров», «Юридическое»),
  внутри — статьи с вложенностью (`parent_id`), порядок задаёт редактор.
- **Редактор** — TipTap (ProseMirror) с набором: заголовки, списки,
  таблицы, картинки, видео (ссылка на Kinescope/VK Video/RuTube и
  загруженный файл), вложения, выноски («важно», «совет»), чек-листы,
  ссылки на другие статьи и на задачи. Содержимое — **JSON-документ
  ProseMirror** в `content jsonb`; из него сервер строит HTML для чтения
  (`content_html`) и чистый текст для поиска (`content_text`). Markdown
  как формат хранения не годится: таблицы, выноски и вложения в нём
  либо не выразить, либо получится свой диалект.
- **Черновик → публикация → архив**; каждая публикация — строка
  `kb_article_versions` (кто, когда, что изменилось), возврат к любой
  версии.
- **Аудитория**: `audience_roles text[]` (коды ролей клуба и УК: `owner`,
  `manager`, `trainer`, `hq`) и `audience_club_status text[]`
  (`opening`, `open`) — политика отбирает строки тем же условием
  `(cardinality(audience_roles) = 0 or audience_roles && (select app.my_role_codes()))`,
  что у Eventbase; статья без аудитории видна всем вошедшим.
- **«Ознакомлен»**: у статьи флаг `requires_ack`; собственник нажимает
  «Ознакомлен» — строка `kb_acks (article_id, version_id, user_id,
  acked_at)`; УК видит отчёт «кто из 300 клубов прочитал новый стандарт»
  и ставит задачу остальным одной кнопкой (связка с продуктом «Задачи»).
- **Чтение**: `kb_reads (article_id, user_id, first_read_at, last_read_at)`
  — отметку ставит браузер после показа (не prefetch), как у Eventbase.
- **Поиск**: Postgres, `tsvector` по `title || content_text` с
  конфигурацией `russian` (морфология), `pg_trgm` для опечаток;
  результат — только видимые статьи (поиск идёт под RLS). Никакого
  Elasticsearch.
- **Вопрос к статье** — открывает чат с автором/разделом поддержки УК
  (продукт «Чаты»), а не комментарии под статьёй: обсуждение живёт там,
  где его читают.
- **Файлы** — приватный бакет `kb-files`, загрузка из браузера по
  подписанному URL, выдача подписанными ссылками по сессии. Картинки
  пережимаются сервером (`sharp`), SVG отклоняется (исполняемый XSS).
- **Шаблоны статей** («Регламент», «Чек-лист открытия») и экспорт в PDF
  — релиз 2.
- **ИИ-помощник редактора** (переписать короче, сделать чек-лист,
  ответить собственнику по базе знаний) — через поставщика Яндекс, релиз 2.

### Таблицы

| Таблица | Колонки | Политики |
|---|---|---|
| `kb_spaces` | `id`, `org_id`, `title`, `slug`, `icon`, `sort_order`, `audience_roles[]`, `is_published` | select по аудитории; write — `has_permission(org,'kb.editor')` |
| `kb_articles` | `id`, `org_id`, `space_id`, `parent_id`, `slug`, `title`, `summary`, `status (draft/published/archived)`, `current_version_id`, `requires_ack`, `audience_roles[]`, `audience_club_status[]`, `sort_order`, `published_at`, `search tsvector generated`, `created_by`, `updated_at` | select: published по аудитории; черновики — редакторам; write — `kb.editor` |
| `kb_article_versions` | `id`, `article_id`, `version_no`, `content jsonb`, `content_html`, `content_text`, `change_note`, `created_by`, `created_at` | select — как статья; insert — редактор; update/delete — нет (история не правится) |
| `kb_attachments` | `id`, `article_id`, `file_id → files`, `title`, `sort_order` | как статья |
| `kb_reads`, `kb_acks` | `(article_id, user_id)`, метки времени, `version_id` | своя строка insert/select; отчёты УК — RPC `kb_ack_report(article)` |

## 2. Задачи (`tasks`)

Замена Битрикс-задач для УК ↔ собственники. Главный сценарий — не
«личный таск-трекер», а **поручение сети**: УК ставит одну задачу на 300
клубов и видит, кто сделал.

### Что умеет

- **Доски** (`task_boards`): у сети (отделы УК: «Маркетинг», «Открытия»,
  «Качество») и у клуба (своя доска у каждой студии, создаётся вместе с
  клубом). Колонки доски — **статусы из справочника доски**
  (`task_statuses`: код, название, цвет, `is_done`), по умолчанию
  «Новая / В работе / На проверке / Готово / Отменена».
- **Задача** (`tasks`): название, описание (тот же редактор, что в базе
  знаний, урезанный), исполнитель, постановщик, наблюдатели, срок,
  приоритет, клуб (если задача про клуб), подзадачи (`parent_id`),
  чек-лист, вложения, метки, связь со статьёй базы знаний.
- **Поручение сети** (`task_assignments`): шаблон задачи + выбор клубов
  (все / по статусу / по региону / список) → по одной задаче на клуб
  исполнителю по роли (`owner` клуба), сводка «сделано 212 из 300»,
  напоминания отстающим одной кнопкой. Это главное отличие от
  Битрикса, где такое делается руками.
- **Повторяющиеся задачи** («ежемесячный отчёт по выручке до 5-го») —
  правило в `task_recurrences`, экземпляры создаёт воркер по `pg_cron`.
- **Комментарии** (`task_comments`) с упоминаниями `@имя` → уведомление;
  **история** (`task_events`: смена статуса, исполнителя, срока) —
  только добавление.
- **Представления**: доска (канбан), список, «Мои задачи» (поручено мне
  / поставлено мной / наблюдаю), календарь сроков; фильтры по клубу,
  исполнителю, метке, просрочке. Списки листаются **курсором**, точного
  «сколько всего» не считаем (урок Eventbase).
- **Уведомления**: назначили, упомянули, сменили статус, срок через
  сутки, просрочено — по каналам из `notification_prefs`.

### Видимость (релиз 1)

| Кто | Видит |
|---|---|
| org admin / staff | все доски сети и всех клубов |
| owner / manager клуба | доска своего клуба, задачи сети, где клуб — исполнитель, свои задачи |
| administrator / trainer | задачи, где он исполнитель/постановщик/наблюдатель, и доска клуба, если включено в настройках клуба |

`app.task_visible(task_id)` — security-definer-функция, одна на все
политики задач и комментариев.

### Таблицы

`task_boards`, `task_statuses`, `tasks`, `task_watchers`, `task_checklist_items`,
`task_comments`, `task_attachments (file_id)`, `task_labels`, `task_label_links`,
`task_events`, `task_assignments`, `task_recurrences`. У всех `org_id`,
у клубных — `club_id`; `updated_at` триггером; счётчики комментариев и
подзадач — колонками, которые держат триггеры (не `count(*)` на показе).

## 3. Чаты (`chat`)

Корпоративный мессенджер: УК ↔ собственники, УК внутри себя, клуб внутри
себя. Основа — чаты приложения участника Eventbase (таблицы, SSE-канал,
идемпотентность, курсоры), с тем, чего там не хватало корпоративному
мессенджеру.

### Что умеет

- **Виды чатов** (`chats.type`): `dm` (личный, ключ `dm_key` из двух id),
  `group` (группа с явным составом), `channel` (канал объявлений: пишут
  админы, читают все подписчики; ответы — тредом или выключены),
  `club` (служебный чат клуба с УК: собственник, управляющий, куратор —
  создаётся вместе с клубом), `task` (обсуждение задачи — тот же
  механизм, привязка `task_id`).
- **Членство явное у всех видов** — в Eventbase у общего чата членства
  не было, и для мессенджера это не годится: нужны список участников,
  роли в чате (`admin`/`member`), выход и исключение.
- **Сообщения**: текст до 4 000 знаков с лёгкой разметкой (жирный,
  ссылки, код, цитата), вложения (файлы до 20 МБ, картинки до 5 МБ,
  голосовые — релиз 2), ответ на сообщение (`reply_to_id`), пересылка,
  реакции, **редактирование и удаление своих** (`edited_at`, `deleted_at`,
  прежний текст — в `chat_message_history`, корпоративный след не
  пропадает), закрепление, упоминания `@`.
- **Прочитанность**: `chat_members.last_read_message_id`; у личного чата
  показывается «прочитано», у группы — «прочитали N» по маркерам
  участников. Непрочитанное считает RPC `chat_list_mine()` с потолком
  «99+».
- **Поиск по сообщениям** — `tsvector russian` по телу сообщений
  видимых чатов.
- **Живое обновление** — SSE-канал, одно соединение на вкладку,
  комната-снимок раз в секунду (ADR `platform-003`); хвост открытой
  переписки дописывается без перерисовки (`api/chat/<id>/tail?after=`).
  «Печатает…» — релиз 2 (эфемерно через комнату инстанса).
- **Уведомления о сообщениях**: личные и упоминания — сразу (push,
  письмо через 10 минут, если не прочитано); группы и каналы — по
  настройке участника (`muted`, дайджест).
- **Модерация**: админ сети может удалить любое сообщение и выключить
  участника из чата; журнал — в `audit_log`.

### Таблицы

| Таблица | Ключевые колонки |
|---|---|
| `chats` | `id`, `org_id`, `type`, `title`, `avatar_path`, `club_id`, `task_id`, `dm_key unique`, `created_by`, `last_message_id`, `last_message_at`, `settings jsonb` |
| `chat_members` | PK `(chat_id, user_id)`, `role`, `joined_at`, `left_at`, `last_read_message_id`, `muted_until`, `notify_mode` — update от участника только `last_read_message_id`, `muted_until`, `notify_mode` через `app.only_columns` |
| `chat_messages` | `id bigint identity`, `chat_id`, `sender_id`, `body`, `body_format`, `reply_to_id`, `forwarded_from_id`, `attachments jsonb` (ссылки на `files`), `client_key` (идемпотентность: unique `(chat_id, sender_id, client_key)`), `edited_at`, `deleted_at`, `pinned_at`, `created_at`; индекс `(chat_id, id desc)` |
| `chat_message_history` | `message_id`, `body_before`, `changed_at` — только добавление |
| `chat_reactions` | PK `(message_id, user_id, emoji)` |
| `chat_mentions` | `(message_id, user_id)` — заполняет триггер; источник уведомлений |

Политика select сообщений — `exists (select 1 from chat_members m where
m.chat_id = chat_id and m.user_id = (select app.staff_id()) and m.left_at
is null)`, обёрнутая в `app.chat_member(chat_id)`.

## 4. PWA портала и уведомления (релиз 1)

- Манифест и service worker — **маршрутами** (`/manifest`, `/sw`), а не
  плагином: Eventbase прошёл это целиком (`start_url` без слеша,
  `skipWaiting`+`clients.claim`, кеш только `/_next/static`, навигация
  не кешируется — чужой профиль на общем телефоне, офлайн-страница
  попыткой, проверка разбора SW в CI).
- Установка на телефон — слой с инструкцией для iPhone/Android (без
  `beforeinstallprompt`); на iPhone push работает только из
  установленного приложения.
- Канал уведомлений — четыре слоя: лента `notifications` в портале
  (всегда), Web Push, письмо (дайджест и «не прочитано за 10 минут»),
  Telegram-бот (по желанию, релиз 2). ADR `platform-004`.

## 5. Клиентское приложение (`apps/client`, релиз 3) — что закладываем сейчас

- **Клиент принадлежит сети**: `clients (id, org_id, phone unique, email,
  first_name, last_name, birth_date, avatar_path, status, consents jsonb,
  created_at)`; связь с клубами — `client_club_links`; абонементы —
  `memberships (client_id, club_id | null для сетевых, plan_id, …)`.
- **Вход по телефону**: код по SMS (российский шлюз) или через бота
  Telegram/MAX; сессия 90 дней со скользящим продлением; таблицы
  `client_sessions`, `client_login_codes`, лимиты по паре «телефон + IP».
- **Клеймы** `cl_client_id`, `cl_org_id`; политики клиентов пишутся
  отдельно от политик сотрудников и проверяются своей матрицей в тесте.
- **Согласия по 152-ФЗ** — `client_consents (client_id, kind, version,
  given_at, ip, source)`; текст политики — статья базы знаний с версией.
- **Платежи** — модули ЮKassa / CloudPayments / Т-Банк из
  `apps/registration` Eventbase переносятся как есть; чеки 54-ФЗ —
  через кассу шлюза.
- **Сборки в магазины** — позже, оболочкой (Capacitor/TWA) над той же
  PWA; архитектуру это не меняет.

## 6. Кабинет клуба (релиз 4) — что закладываем сейчас

- Разделы кабинета живут в том же `apps/portal`, под клубом:
  `/clubs/<id>/clients`, `/schedule`, `/crm`, `/inbox`.
- **Единое окно переписки с клиентами** — отдельные таблицы
  `im_channels (club_id, kind: telegram|max|vk|phone, credentials → секреты
  только в таблице без политик)`, `im_conversations (client_id, channel_id,
  assigned_to)`, `im_messages`. **WhatsApp в России заблокирован с февраля
  2026** — канал не планируется; Telegram Bot API и MAX Bot API (нужна
  верификация юрлица в «MAX для бизнеса») — первые два канала, VK — третий.
- **Воронка лидов** (`crm_leads`, `crm_stages`, `crm_activities`) с
  импортом из amoCRM.
- **Расписание** (`schedule_slots`, `schedule_bookings`, `rooms`,
  `trainers` = `club_members` с ролью `trainer`), запись и лист ожидания
  с замками в базе (гонки «3 места — 20 запросов» решаются
  `pg_advisory_xact_lock`, как в Eventbase).

Эти таблицы не создаются в релизе 1, но имена сущностей и принадлежность
клиента сети зафиксированы здесь, чтобы задачи, чаты и уведомления
релиза 1 не пришлось переделывать.

## 7. Матрица видимости релиза 1 (кратко)

| Данные | super_admin | org admin | org staff | club owner/manager | club administrator/trainer |
|---|---|---|---|---|---|
| Все клубы, люди, роли | ✓ | ✓ | читает | свой клуб (люди клуба — правит owner/manager) | свой клуб, читает |
| База знаний | ✓ | пишет | читает; пишет с `kb.editor` | читает по аудитории | читает по аудитории |
| Доски сети | ✓ | ✓ | ✓ | задачи, где клуб исполнитель | нет |
| Доска клуба | ✓ | ✓ | ✓ | ✓ | по настройке клуба / свои задачи |
| Чаты | только свои + модерация | свои + модерация | свои | свои | свои |
| Журнал действий | ✓ | по своей сети | нет | нет | нет |
| Аналитика сети | ✓ | ✓ | по правам | по своему клубу | нет |

Личные чаты и личные уведомления не читает никто, кроме участников, —
включая супер-админа; модерация удаляет сообщение, не читая переписку
целиком (RPC с журналом).
