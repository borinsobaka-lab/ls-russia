# Безопасность, персональные данные, устойчивость

Статус: предложено — 2026-10-08. Собрано из ответа на аудит Eventbase
«Участник как нападающий» (23.09.2026), аудита экосистемы (30.09.2026),
правил `apps/admin` и `apps/event-app`, ADR event-app-003/005 и
checkin-001. Это не список пожеланий, а то, что проверяется кодом,
тестом и CI.

## 1. Модель угроз

Кто нападает и чем:

1. **Вошедший сотрудник или собственник** — подделанные тела запросов,
   чужие идентификаторы в адресе, залпы запросов, вторая вкладка. Самый
   вероятный противник: 300–400 человек с разными интересами (франчайзи
   против франчайзи, уволенный сотрудник с живой сессией).
2. **Украденная сессия** — телефон без блокировки, общий компьютер на
   ресепшене.
3. **Утечка секрета площадки** — ключ `service_role`, пароль базы, ключ S3.
4. **Внешний аноним** — перебор паролей и кодов, спам в публичные формы
   (релиз 3), DDoS.
5. **Уволенный с правами** — задержка отзыва доступа.
6. **Сам оператор** — ошибка в коде, удаливший не ту строку скрипт,
   выкат с кривой миграцией.

## 2. Что защищает (слоями)

### 2.1. Изоляция живёт в базе

- RLS на каждой таблице, четыре политики по операциям, функции прав из
  `02-data-model.md` § 3–4. Приложение не фильтрует «по клубу» в коде —
  фильтрует Postgres. Класс ошибок «забыли `.eq('club_id')`» исключён.
- `service_role` — только в перечисленных модулях (ADR `platform-001`,
  § «Где разрешён service_role»). Проверка механическая:
  `scripts/check-service-role.mjs` в CI падает на вызове `adminClient()`
  вне списка файлов.
- Личность сотрудника существует только после второго фактора
  (`app.staff_id()` требует `aal2`), и это проверяет тест: сессия `aal1`
  не читает ни одной строки.
- Белые списки колонок (`app.only_columns`) на каждом update от рядового
  пользователя; сверка сети/клуба цели ссылки в `with check`.
- Служебные данные (сессии клиентов, токены, коды, подписки, журнал)
  — таблицы без политик, читает только сервер.

### 2.2. Вход сотрудников (ADR `platform-002`)

- Почта + пароль (минимум 12 знаков, проверка по словарю утечек —
  локальный список, не внешний API: HaveIBeenPwned из РФ ненадёжен) +
  **TOTP** обязателен для всех. Запись в базе возможна только с `aal2`.
- Учётки создаются только приглашением (`GOTRUE_DISABLE_SIGNUP=true`,
  письмо шлёт платформа, а не GoTrue). `/auth/confirm` **не выдаёт
  сессию** — урок Eventbase #589: ссылка из письма обходила второй фактор.
- Ссылки сброса пароля и приглашений — свои токены (`sha256` в
  `invitations`/`auth_reset_tokens`, срок 60 минут / 7 дней, гасятся
  при выдаче новых и при использовании атомарно `update … where used_at
  is null`), адрес ссылки собирается **только** из `PORTAL_PUBLIC_URL`,
  никогда из `Host`/`X-Forwarded-Host` (отравление ссылки сброса).
- Лимиты входа — в таблице `auth_rate_events`, не в памяти (реплик
  несколько): неудачные пароли 10/15 мин на адрес и 25/15 мин на IP,
  попытки TOTP 6/10 мин, сброс пароля 5/час. **Временный троттл, а не
  вечная блокировка** — иначе жертву запирают чужими попытками.
- Ответ на «восстановить пароль» одинаков для своих и чужих адресов;
  лимит считается до поиска профиля.
- Refresh-токены ротируются (`GOTRUE_SECURITY_REFRESH_TOKEN_ROTATION_ENABLED`);
  access-токен час. Выход гасит все сессии пользователя (`signOut({scope:
  'global'})`), блокировка учётки (`profiles.status = 'blocked'`) делает
  `app.staff_id()` пустым **немедленно**, не дожидаясь истечения токена —
  это и есть ответ на угрозу «уволенный с правами».
- Выход — POST с проверкой `Sec-Fetch-Site`/`Origin`; серверные действия
  защищены проверкой Origin в Next.
- Аварийный доступ: сброс TOTP-фактора супер-админом через админ-API
  GoTrue из веб-терминала, с записью в `audit_log`; порядок — в runbook
  аварийного доступа (пишется вместе с модулем входа).

### 2.3. Клиенты (релиз 3)

- Свои сессии (случайный токен в куке `httpOnly; secure; sameSite=lax`,
  sha256 в базе), короткий JWT с клеймами в своём пространстве имён
  (`cl_*`), подписанный на каждый запрос.
- Код по SMS: 6 цифр, 10 минут, ≤5 попыток, попытка списывается
  **атомарно до сравнения** (гонка двух вкладок), лимиты по паре
  «телефон + IP» (чужой номер нельзя запереть с чужого устройства) и
  широкий потолок по номеру, ответ не раскрывает наличие номера в базе.
- Телефон, вписанный клиентом в профиль, — **не личность, пока не
  подтверждён кодом** (`phone_unconfirmed`; урок В4 Eventbase: вписанная
  чужая почта подсаживала владельца в чужую строку).
- Лимит по IP — это лимит на весь клуб за NAT (`CROWD_PER_IP`).

### 2.4. Файлы

- Все бакеты **приватные**, чтение — подписанными ссылками, которые
  выдаёт сервер после проверки RLS-запросом «эта строка мне видна»;
  ссылки кешируются 50 минут при сроке 60 (стабильный адрес = кеш
  браузера).
- Загрузка — из браузера напрямую в Storage по одноразовому подписанному
  URL; **путь выбирает сервер**, форма увозит только путь, действие
  проверяет префикс и существование файла.
- MIME и размер — на бакете (`allowed_mime_types`, `file_size_limit`) и
  повторно в коде; SVG отклоняется везде (исполняемый XSS); картинки
  пережимаются сервером с потолком пикселей (картинки-бомбы), один
  модуль-вход для `sharp`.
- Реестр `files`: удаление строки-носителя удаляет файл; удаление клуба
  — все его файлы; проверяется тестом.

### 2.5. Приложение

- Заголовки безопасности ставит middleware на каждый ответ: CSP
  (`default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`,
  источники — из переменных окружения, не из кода), HSTS год,
  `X-Content-Type-Options`, `Referrer-Policy: strict-origin-when-cross-origin`,
  `Permissions-Policy` (`camera=(self)`, а не `camera=()` — запрет бьёт
  по своему сканеру). `script-src 'unsafe-inline'` остаётся, пока App
  Router не отдаёт nonce; `scripts/check-csp.mjs` стережёт, чтобы CSP не
  погасила страницу.
- Тела запросов читаются потоком с пределом и таймаутом (`readLimited`),
  `Content-Length` не верим; потолок на прокси 2 МБ (Traefik `buffering`).
- Серверные пределы длины на всё, что пишет человек (сообщение 4 000,
  название задачи 200, комментарий 4 000, поле профиля 200) + `check`
  в базе как последний рубеж.
- Идемпотентность записей от клиента (`client_key` у сообщений и
  комментариев): повтор запроса — успех, а не дубль.
- Счётчики под advisory-замками, лимиты «на объект» — в базе, ведро в
  памяти — только передний край и делится на число реплик.
- Редиректы из обработчиков — только относительный `Location`; параметр
  `next` проходит `safePath` (`//evil.example` — абсолютный адрес).
- Ошибки наружу — класс причины (`forbidden`, `duplicate`, `check`,
  `schema`, `fail`) и код базы; `details` с значениями полей — никогда.
- Логи и GlitchTip без персональных данных: заголовки по белому списку,
  `sendDefaultPii: false`, cookies и query вырезаны, от пользователя —
  только `id`.

### 2.6. Инфраструктура

- Файрвол Timeweb: 22 с одного IP, 80/443 всем, остальное закрыто;
  Coolify и Studio — за TLS и паролем, порт 8000 закрыт.
- SSH только по ключу, `fail2ban`, `unattended-upgrades`, образ сервера
  перед изменениями.
- Секреты — менеджер паролей + переменные Coolify; ротация раз в год и
  при уходе любого, кто их видел; `JWT_SECRET` ротируется сменой
  переменной (сессии сотрудников перелогинятся, клиентские куки —
  переживут, у них токен случайный).
- Бэкапы в другой город, шифрование дампов перед выгрузкой в S3 (`age`
  ключом владельца) — отдельной задачей после запуска; проверка
  восстановления раз в квартал.
- Зависимости: `pnpm audit --prod` в CI (не блокирует), Renovate —
  релиз 2.

Разработчику важно понимать одно: **технические меры из этого документа
покрывают требования, а бумага (уведомление, политика, договоры) — на
операторе**. Без бумаги штрафы, без мер — утечка.

## 4. Регулярные проверки

- **Аудит «пользователь как нападающий»** — раз в квартал и перед каждым
  большим релизом: сессия Claude Code получает роль рядового
  собственника и инструкцию ломать (подмена id, залпы, права на update).
  Каждая находка воспроизводится SQL-тестом в `supabase/tests/NN-audit-*.sql`
  до исправления, как в Eventbase (40-participant-audit.sql).
- **Матрица видимости в CI** — на каждый PR с миграцией.
- **Проверка восстановления бэкапа** — раз в квартал, дата в паспорте
  площадки.
- **Ротация секретов** — раз в год и по событию.
- **Пересмотр ролей**: отчёт «кто имеет доступ к клубу X» собственнику
  раз в квартал письмом (релиз 2).
