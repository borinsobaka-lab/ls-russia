# Безопасность, персональные данные, устойчивость

Статус: предложено — 2026-10-08. Это не список пожеланий: каждый пункт
проверяется кодом, тестом или CI.

## 1. Модель угроз

1. **Вошедший сотрудник или собственник** — подделанные тела запросов,
   чужие идентификаторы в адресе, залпы запросов, вторая вкладка. Самый
   вероятный противник: сотни людей с разными интересами, уволенный с
   живой сессией.
2. **Украденная сессия** — телефон без блокировки, общий компьютер на
   ресепшене.
3. **Утечка секрета площадки** — ключ `service_role`, пароль базы, ключ S3.
4. **Внешний аноним** — перебор паролей и кодов, спам в публичные формы
   (релиз 3), DDoS.
5. **Уволенный с правами** — задержка отзыва доступа.
6. **Сам оператор** — ошибка в коде, не тот скрипт, кривая миграция.

## 2. Меры

### 2.1. Изоляция в базе

- RLS на каждой таблице, четыре политики по операциям, функции прав
  (`03-data-model.md` § 3–4). Приложение не фильтрует «по клубу» —
  фильтрует Postgres.
- `service_role` — только в закрытом списке модулей (ADR
  `platform-001`); `scripts/check-service-role.mjs` в CI падает на
  вызове `adminClient()` вне списка.
- Личность сотрудника существует только после второго фактора
  (`app.staff_id()` требует `aal2`); тест проверяет, что сессия `aal1`
  не читает ни одной строки.
- Белые списки колонок (`app.only_columns`) на update от рядового
  пользователя; сверка сети/клуба цели ссылки в `with check`.
- Служебные таблицы (сессии клиентов, токены, коды, подписки, журнал)
  — без политик, читает только сервер.

### 2.2. Вход сотрудников (ADR `platform-002`)

- Почта + пароль (минимум 12 знаков; проверка по локальному списку
  утёкших паролей, не по внешнему API) + **TOTP** обязателен. Запись в
  базе возможна только с `aal2`.
- Учётки — только приглашением (`GOTRUE_DISABLE_SIGNUP=true`); письмо
  шлёт платформа. Маршрут подтверждения из письма **сессию не выдаёт**
  — иначе ссылка обходит второй фактор.
- Ссылки сброса пароля и приглашений — свои токены (`sha256`, 60 минут /
  7 дней, гасятся при выдаче новых; потребление атомарно `update …
  where used_at is null`), адрес ссылки — только из `PORTAL_PUBLIC_URL`,
  никогда из `Host`/`X-Forwarded-Host`.
- Лимиты входа — в таблице `auth_rate_events` (реплик несколько):
  неудачные пароли 10/15 мин на адрес и 25/15 мин на IP, TOTP 6/10 мин,
  сброс 5/час. Временный троттл, не вечная блокировка — иначе жертву
  запирают чужими попытками.
- Ответ на «восстановить пароль» одинаков для своих и чужих адресов;
  лимит считается до поиска профиля.
- Refresh-токены ротируются; access-токен — час. Блокировка учётки
  (`profiles.status = 'blocked'`) делает `app.staff_id()` пустым
  **немедленно** — ответ на угрозу «уволенный с правами». Выход гасит
  все сессии (`scope: 'global'`).
- Выход — POST с проверкой `Sec-Fetch-Site`/`Origin`.
- Аварийный сброс TOTP — супер-админом через админ-API GoTrue из
  веб-терминала с записью в `audit_log`.

### 2.3. Клиенты (релиз 3)

- Свои сессии (случайный токен в куке `httpOnly; secure; sameSite=lax`,
  sha256 в базе), короткий JWT с клеймами `cl_*`, подписываемый на
  каждый запрос.
- Код по SMS: 6 цифр, 10 минут, ≤5 попыток, попытка списывается
  **атомарно до сравнения**; лимиты по паре «телефон + IP» и широкий
  потолок по номеру; ответ не раскрывает наличие номера.
- Телефон, вписанный клиентом в профиль, — не личность, пока не
  подтверждён кодом (`phone_unconfirmed`): иначе вписанный чужой номер
  подсаживал бы владельца в чужую строку.
- Лимит по IP — лимит на весь клуб за NAT.

### 2.4. Файлы

- Все бакеты приватные; чтение — подписанными ссылками после
  RLS-проверки строки-носителя; ссылки кешируются 50 минут при сроке 60.
- Загрузка — из браузера напрямую в Storage по одноразовому подписанному
  URL; путь выбирает сервер; форма увозит только путь; действие
  проверяет префикс и существование файла.
- MIME и размер — на бакете и повторно в коде; SVG отклоняется везде;
  картинки пережимаются сервером с потолком пикселей; один модуль-вход
  для `sharp`.
- Реестр `files`: удаление строки-носителя удаляет файл; удаление клуба
  — все его файлы; проверяется тестом.

### 2.5. Приложение

- Заголовки безопасности ставит middleware на каждый ответ: CSP
  (`default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`;
  источники из переменных окружения), HSTS год,
  `X-Content-Type-Options`, `Referrer-Policy: strict-origin-when-cross-origin`,
  `Permissions-Policy` (`camera=(self)`: `camera=()` запрещает камеру и
  своему сканеру). `script-src 'unsafe-inline'` остаётся, пока App Router
  не отдаёт nonce; `scripts/check-csp.mjs` стережёт, что `script-src`
  задан и страница не гаснет.
- Тела запросов читаются потоком с пределом и таймаутом;
  `Content-Length` не верим; потолок на прокси 2 МБ.
- Серверные пределы длины на всё, что пишет человек, + `check` в базе.
- Идемпотентность записей (`client_key`): повтор запроса — успех, не
  дубль.
- Счётчики и лимиты «на объект» — под advisory-замками в базе; ведро в
  памяти — передний край, делится на число реплик.
- Редиректы из обработчиков — относительный `Location`; параметр `next`
  проходит проверку (`//evil.example` — абсолютный адрес).
- Ошибки наружу — класс причины и код базы; `details` со значениями
  полей — никогда.
- Логи и GlitchTip без персональных данных: заголовки по белому списку,
  `sendDefaultPii: false`, cookies и query вырезаны, от пользователя —
  только `id`.

### 2.6. Инфраструктура

- Файрвол: 22 с одного IP, 80/443 всем; Coolify и Studio за TLS и
  паролем; порт 8000 закрыт.
- SSH только по ключу, `fail2ban`, `unattended-upgrades`, образ сервера
  перед изменениями.
- Секреты — менеджер паролей + Coolify; ротация раз в год и при уходе
  любого, кто их видел; смена `JWT_SECRET` перелогинивает сотрудников,
  клиентские куки переживают (токен случайный).
- Бэкапы в другой город; шифрование дампов перед S3 (`age`) — задача
  после запуска; проверка восстановления раз в квартал.
- `pnpm audit --prod` в CI; Renovate — релиз 2.

## 3. 152-ФЗ — что нужно, кроме «серверы в России»

| Шаг | Кто | Когда |
|---|---|---|
| Определить оператора ПД (УК сети) и обработчика (разработчик по договору поручения) | 🔴 владелец + юрист | до пилота |
| Уведомление в Роскомнадзор о начале обработки (или уточнение действующего) | 🔴 оператор | до пилота |
| Соглашения об обработке ПД с Timeweb, Unisender, SMS-шлюзом | 🔴 оператор | до запуска |
| Политика обработки ПД и согласия: сотрудники — в договорах; клиенты — галочкой с версией (`client_consents`) | 🔴 юрист, 🤖 реализация | релиз 1 / 3 |
| Локализация: база, файлы, бэкапы, логи ошибок — в РФ. Push через Google/Apple **без персональных данных в теле** | 🤖 | релиз 1 |
| Журнал доступа `audit_log` — 365 дней, IP обезличивается | 🤖 | релиз 1 |
| Удаление по требованию: стирание сотрудника/клиента с обезличенным следом («Удалённый пользователь»), файлы удаляются | 🤖 | релиз 1 / 3 |
| Инциденты: при утечке оператор уведомляет РКН **в течение 24 часов** о факте и **72 часов** о результатах разбора; нужен runbook и ответственный | 🔴 + 🤖 | до запуска |
| Уровень защищённости (ПП-1119) и меры (приказ ФСТЭК № 21): для сети студий без спецкатегорий и биометрии — как правило УЗ-3/УЗ-4, технические меры покрываются этим документом, остальное — организационные документы | 🔴 юрист/ИБ | к релизу 3 |

Технические меры — на платформе; бумага (уведомление, политика,
договоры) — на операторе. Без бумаги штрафы, без мер — утечка.

## 4. Регулярные проверки

- **Аудит «пользователь как нападающий»** — раз в квартал и перед
  большим релизом: сессия Claude Code с ролью рядового собственника и
  инструкцией ломать. Каждая находка воспроизводится SQL-тестом
  `supabase/tests/NN-audit-*.sql` до исправления.
- **Матрица видимости в CI** — на каждый PR с миграцией.
- **Проверка восстановления бэкапа** — раз в квартал, дата в паспорте
  площадки.
- **Ротация секретов** — раз в год и по событию.
- **Пересмотр ролей**: отчёт «кто имеет доступ к клубу» собственнику раз
  в квартал (релиз 2).
