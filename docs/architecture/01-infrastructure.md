# Инфраструктура и сервисы платформы Lady Stretch

Статус: предложено — 2026-10-08 (на основе опыта Eventbase: ADR
`infra-001-russia-contour`, runbook `11-timeweb-second-contour`,
`35-eu-self-hosted-supabase`, `11-observability-and-quality`).

Документ отвечает на вопрос «из чего собрана платформа и почему именно из
этого». Пошаговый порядок покупки и настройки — `docs/setup/01-timeweb-server.md`.

## 1. Исходные требования

- Сеть студий растяжки: сотни клубов по России, тысячи клиентов, 300–400
  активных пользователей внутреннего контура (сотрудники управляющей
  компании и собственники студий) в первом релизе.
- **Все данные — в России.** Персональные данные граждан РФ (сотрудники,
  собственники, позже клиенты) хранятся в базе на территории РФ (152-ФЗ).
  Никаких SaaS-сервисов с данными за границей: ни мониторинга, ни почты,
  ни аналитики.
- Один веб-сервис для сотрудников (база знаний, задачи, чаты, позже кабинет
  клуба) и отдельное клиентское приложение (PWA, позже сборки в магазины).
- Разработка — Claude Code в вебе, несколько параллельных сессий. Значит
  инфраструктура обязана выкатываться сама по слиянию в `main`, без ручных
  шагов (урок Eventbase: ручное применение миграций останавливало выкаты
  на полсуток).
- Старт — минимальная конфигурация, рост — по мере нагрузки.

## 2. Итоговый стек

| Слой | Решение | Почему именно оно |
|---|---|---|
| Хостинг | **Timeweb Cloud**, облачный сервер в Москве, Ubuntu 24.04 | В реестре хостеров РКН, трафик серверов не тарифицируется, почасовая оплата, S3/CDN/DNS/файрвол/балансировщик в одной панели. Проверено российской площадкой Eventbase с 21.08.2026 |
| Платформа выката | **Coolify** (self-hosted PaaS) | Деплой по push в `main`, TLS сам, логи, веб-терминал, бэкапы баз в S3. Опыт двух площадок Eventbase |
| База, вход, файлы | **Supabase на своём сервере** (Postgres + GoTrue + PostgREST + Storage + Kong + imgproxy + Studio) | Мультитенантность через RLS, готовый Auth со вторым фактором (TOTP), PostgREST как единый API к базе. Supabase Cloud в РФ нет; managed Postgres Timeweb не даёт суперпользователя и расширений, нужных схемам `auth`/`storage` (вывод Eventbase) |
| Файлы | **Timeweb S3** как бэкенд Supabase Storage (`STORAGE_BACKEND=s3`) + отдельный бакет под бэкапы | Сервер остаётся stateless, диск не растёт, бэкапы лежат в другом ЦОД (S3 Timeweb — Санкт-Петербург, сервер — Москва) |
| Приложения | **Next.js 15 (App Router) + React 19 + TypeScript + Tailwind 4**, pnpm-монорепо, standalone-сборка, образы `node:22-alpine` | Ровно тот стек, на котором написаны 9 приложений Eventbase: все наработки (клиенты Supabase, `mustWrite`, SSE-канал, очередь задач, PWA, service worker) переносятся без перевода |
| Realtime | **SSE с откатом на опрос**, комната-снимок внутри процесса (ADR `platform-003-realtime`) | Проверено на залах 5 000 человек; не нужны ни Supabase Realtime, ни Redis, ни WebSocket |
| Очередь и расписание | Таблица `jobs` в Postgres (`for update skip locked`), воркер — вторая копия того же образа, `pg_cron` для расписаний | Ни одной лишней службы; очередь переживает рестарт; транзакционно с данными |
| Почта | **Unisender Go** (HTTP API, домен-отправитель с DKIM/SPF/DMARC) | Российский транзакционный отправитель; Resend/SES за Cloudflare и из РФ работают через раз |
| Уведомления | Лента в приложении (всегда) + Web Push (VAPID) + письма-дайджесты + Telegram-бот (опционально) | Push на Android идёт через FCM (Google), на iPhone — только из установленной PWA; поэтому лента в приложении — основной канал, остальные — ускорители |
| Ошибки | **GlitchTip** (совместим с SDK Sentry), self-hosted в Coolify | Sentry SaaS не проходит по 152-ФЗ |
| Аптайм | **Uptime Kuma**, тревоги в Telegram | Бесплатно, шаблон Coolify |
| Метрики и логи | **Grafana + Prometheus + Loki + Alloy** — вторым этапом, на отдельном сервере-наблюдателе | На старте достаточно GlitchTip + Kuma; стек метрик ставится, когда появится клиентское приложение и нагрузка |
| CI | **GitHub Actions**, только на PR, только по затронутому (`scripts/ci-affected.sh`), полный прогон раз в неделю | Минуты платные: Eventbase сжёг месячный лимит за три недели, пока не перешёл на «проверки по затронутому» |
| ИИ (позже) | **Яндекс** (AI Studio / SpeechKit / Vision) через поставщика проекта | API Anthropic из России не открывается, API Сбера требует сертификатов НУЦ; Яндекс работает из РФ на обычных сертификатах и держит данные в РФ |
| Капча (публичные формы, позже) | Yandex SmartCaptcha | Прямая замена Turnstile, бесплатна |
| SMS (клиенты, позже) | Российский SMS-шлюз (SMS Aero / SMSC / MTS Exolve) через хук отправки GoTrue или свой модуль | Понадобится входу клиентов по телефону; на первом релизе не нужен |
| Платежи (позже) | ЮKassa / CloudPayments / Т-Банк (модули уже написаны в Eventbase, `apps/registration/src/lib/payments/`) | Абонементы в клиентском приложении, чеки по 54-ФЗ |

### Чего в стеке НЕТ намеренно

- **Cloudflare и зарубежные CDN** — из России рвутся на ECH; домен и DNS
  живут у Timeweb.
- **Supabase Realtime, Redis, Kafka, ClickHouse, Elasticsearch** — каждая
  лишняя служба это ещё один процесс, который надо обновлять, бэкапить и
  поднимать ночью. Полнотекстовый поиск — средствами Postgres
  (`tsvector` с конфигурацией `russian` + `pg_trgm`), очередь — Postgres,
  realtime — процесс приложения.
- **Edge Functions Supabase** — вся серверная логика живёт в приложениях
  Next.js и функциях базы.
- **`next/font/google`** — ходит в интернет во время сборки и роняет выкат;
  шрифты лежат файлами в репозитории.
- **Любой `if (россия)` в коде** — площадка одна, но правило остаётся:
  адреса, ключи и отправители только в переменных окружения.

## 3. Схема сервера на старте

Один сервер **Timeweb Cloud, Москва, 4 vCPU / 8 ГБ / 80 ГБ NVMe**
(тариф линейки Cloud ~1 100 ₽/мес; Premium-линейка той же конфигурации,
которую брал Eventbase, — ~1 800 ₽/мес) плюс swap 4 ГБ.

Почему не меньше. Самая маленькая конфигурация (2 vCPU / 4 ГБ) не
выдержит одновременно стек Supabase (~2–2,5 ГБ в покое), Coolify (~1 ГБ)
и пик сборки Next.js (шаг «Collecting build traces» сканирует
`node_modules` всего монорепо; на 4 ГБ без swap падает молча по OOM).
Тариф у Timeweb меняется только в бо́льшую сторону — поэтому берём с
запасом на год, а не на месяц.

Что живёт на сервере:

| Служба | Память в покое (ориентир) | Примечание |
|---|---|---|
| Coolify (панель, Traefik, Postgres, Redis панели) | ~1 ГБ | Порт 8000 закрывается после первого входа |
| Supabase: `db`, `kong`, `auth`, `rest`, `storage`, `imgproxy`, `meta`, `studio` | ~2–2,5 ГБ | `realtime`, `functions`, `analytics` выключены |
| `portal` (веб, 1 реплика) | ~200–300 МБ | Next.js standalone |
| `portal-worker` (тот же образ, `PORTAL_ROLE=worker`) | ~150 МБ | Очередь `jobs`, письма, push, дайджесты |
| GlitchTip (web + worker + Postgres + Valkey) | ~700 МБ | Можно отложить на 2–4 недели и начать с Kuma |
| Uptime Kuma | ~100 МБ | SQLite |
| Пик сборки образа | до 3–4 ГБ | уходит в swap; сборка идёт на этом же сервере |

Итого ~5 ГБ в покое при 8 ГБ. Этого хватает на 300–400 пользователей с
чатами: расчёт Eventbase — «2 vCPU держат одно мероприятие на несколько
сотен человек с SSE-каналами».

### Когда и что расширять

1. **Появился второй продукт в бою и/или тесно по памяти** → второй сервер
   «наблюдатель» 2 vCPU / 4 ГБ (~1 200 ₽/мес с IPv4): туда переезжают
   GlitchTip, Kuma, ставятся Grafana/Prometheus/Loki. Подключается к тому
   же Coolify вторым сервером по приватной сети (VPC).
2. **Запуск клиентского приложения (тысячи клиентов)** → база на отдельный
   сервер (8 vCPU / 16 ГБ NVMe), приложения остаются на первом; при пиках
   — временные реплики `portal`/`client` из образа за балансировщиком
   Timeweb (почасовая оплата). Схема «вширь, а не ввысь» — из Eventbase.
3. **Сборки стали мешать работе** → сборка образов в GitHub Actions с
   публикацией в GHCR, Coolify только тянет готовый образ. Пока сборок
   мало — собираем на сервере (бесплатно и просто).

## 4. Сеть, домены, TLS

- Домен покупается в Timeweb (для `.ru` нужна верификация владельца:
  паспорт или ЕСИА) и сразу живёт на их NS. Все записи с TTL 300.
- Поддомены: `office.<домен>` или `my.<домен>` — портал сотрудников
  (имя выбирает владелец), `app.<домен>` — клиентское приложение (позже),
  `api.<домен>` — Kong/Supabase, `files.<домен>` — публичный бакет S3
  (если понадобится), `coolify.<домен>`, `status.<домен>`,
  `errors.<домен>`.
- TLS — Let's Encrypt через прокси Coolify (Traefik). Выпуск требует
  публичного IPv4 и заранее прописанной A-записи. Сертификаты НУЦ
  Минцифры для веба не годятся: Safari и Chrome им не доверяют.
- Файрвол Timeweb: 22 — только с IP владельца (и из VPC), 80/443 — всем,
  остальное закрыто. **Группа файрвола Timeweb — allow-list и на
  исходящий трафик тоже**: исходящие TCP/UDP/ICMP по v4 и v6 надо
  разрешить явно, иначе сервер не достучится ни до GitHub, ни до S3.
- Зеркало Docker Hub: `https://dockerhub.timeweb.cloud` в
  `/etc/docker/daemon.json` — Docker Hub стоит за Cloudflare и из РФ
  тянется с обрывами.
- Telegram Bot API из российских ЦОД открывается **только по IPv6** —
  если боту быть, в Docker включается IPv6 в сетях по умолчанию.
- DDoS-защита L3–L4 входит в тариф при размещении в VPC Москвы или СПб.
  L7-защита (DDoS-Guard, StormWall, Qrator — десятки тысяч ₽/мес) — только
  под реальную атаку и только для публичных страниц клиентского
  приложения.

## 5. Бэкапы и восстановление (с первого дня, не «потом»)

- **База**: встроенные бэкапы Coolify у ресурса Postgres — ежедневно,
  хранение 30 дней, назначение — бакет `ls-backups` в Timeweb S3 (класс
  Cold, другой город). Дополнительно — еженедельный `pg_dump` в тот же
  бакет с хранением полгода (задача `pg_cron` + воркер или cron на хосте).
  PITR на self-hosted нет: **RPO — сутки**. Если бизнес потребует меньше —
  WAL-архивирование (`wal-g`/`pgBackRest`) отдельной задачей.
- **Файлы**: лежат в S3; включить версионирование бакета `ls-files` —
  защита от случайного удаления. Отдельного бэкапа S3 не нужно.
- **Сервер**: образ (snapshot) перед каждым изменением инфраструктуры и
  «Защита от удаления» в панели Timeweb.
- **Проверка восстановления** — раз в квартал и после каждого изменения
  схемы бэкапов: поднять временный контейнер Postgres, `pg_restore`
  свежего дампа, пересчитать строки ключевых таблиц. Команды — в
  `docs/setup/01-timeweb-server.md`, раздел «Бэкапы».
- **Секреты**: только в менеджере паролей владельца и в переменных
  Coolify. В репозитории, чате и документах — никогда. Пароль базы,
  `service_role`, `JWT_SECRET`, ключи S3 и Unisender — этого достаточно,
  чтобы увезти все данные.

## 6. Наблюдаемость — что и в каком порядке

Порядок из `11-observability-and-quality.md` Eventbase, сокращённый под
один сервер:

1. **Неделя 1**: `/api/health` у портала и воркера (всегда 200, с
   `?strict=1` — 503 при тревоге), Uptime Kuma с тревогами в Telegram,
   пульс воркера push-монитором (`HEARTBEAT_URL`).
2. **Недели 2–4**: GlitchTip, SDK Sentry в портале (`@sentry/nextjs`) с
   вырезанием персональных данных по белому списку заголовков,
   `sendDefaultPii: false`, DSN отдаётся браузеру атрибутами `<html>`
   (не `NEXT_PUBLIC_*`, чтобы образ был один на любое окружение).
3. **К клиентскому приложению**: сервер-наблюдатель, Grafana + Prometheus
   + Loki, Alloy на ядре (экспортёры node/cadvisor/postgres, логи
   контейнеров), дашборды 1860 / 14282 / 9628 / 13639, тревоги: диск > 85 %,
   память > 90 %, CPU > 85 %, соединений Postgres > 80, `absent(up)`.
   Хранение метрик и логов — 30 дней, событий GlitchTip — 90.

## 7. Ориентировочная стоимость

| Статья | ₽/мес |
|---|---|
| Сервер 4 vCPU / 8 ГБ / 80 ГБ NVMe (Москва) | 1 100–1 800 |
| Публичный IPv4 | ~200 (если не входит в тариф) |
| S3 (файлы + бэкапы, первые десятки ГБ) | 100–300 |
| Домен `.ru` | ~70 (в год ~800) |
| Unisender Go | по объёму; старт — бесплатный пакет, далее от ~1 000 |
| Опции Timeweb: «Отмена удаления», «Аварийная копия» | по 200 каждая |
| GitHub (Free: 2 000 минут CI) | 0 |
| **Итого на старте** | **~2 000–4 000 ₽/мес** |

С наблюдателем (+1 200), отдельной базой (+3 000–5 000), SMS и платёжным
шлюзом — к запуску клиентского приложения ориентир 8–15 тыс. ₽/мес.
Это на порядок дешевле Битрикса на 300–400 пользователей.

## 8. Открытые вопросы владельцу

1. Домен и внешние имена продуктов (портал, клиентское приложение).
2. Кто юридически оператор персональных данных — управляющая компания
   сети (скорее всего) — и от чьего имени подаётся уведомление в РКН.
   Разработчик платформы выступает обработчиком по договору поручения.
3. Нужен ли Telegram-бот как канал уведомлений сотрудникам в первом
   релизе (дёшево, очень удобно в РФ) или достаточно push и писем.
