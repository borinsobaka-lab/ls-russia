# Платформа Lady Stretch — правила работы в этом репозитории

Платформа диджитал-продуктов для сети студий растяжки: портал
сотрудников и собственников (база знаний, задачи, чаты; позже кабинет
клуба) и клиентское приложение. Язык интерфейсов, комментариев,
документации **и переписки с владельцем — русский**: отчёт о работе,
вопрос, объяснение решения — всё по-русски, включая заголовки и подписи.

Статус репозитория (08.10.2026): **документы плана написаны, кода ещё
нет.** Начинать с `docs/architecture/00-master-plan.md`, затем
`docs/setup/02-repo-bootstrap.md`.

## Структура (целевая)

```
apps/portal/        # портал сотрудников и собственников (Next.js 15, App Router, Tailwind 4); он же воркер при PORTAL_ROLE=worker
apps/client/        # клиентское приложение (релиз 3)
packages/shared/    # ОБЩИЕ КОНТРАКТЫ: доменные типы, зеркалящие схему; коды прав; схема редактора
supabase/migrations # ОБЩИЙ КОНТРАКТ: схема Postgres + RLS-политики (только добавление)
supabase/tests/     # исполняемые тесты изоляции; run.sh поднимает одноразовый Postgres
scripts/            # проверки CI и операционные скрипты
docs/architecture/  # план, модель данных, продукты, безопасность, ADR — читать перед работой
docs/setup/         # runbook'и площадки и процессов
docs/patterns/      # правила по темам, на которые ссылается CLAUDE.md приложения
```

Прочти перед работой: `docs/architecture/02-data-model.md` (роли, RLS,
миры доступа) и `docs/architecture/03-products.md` (что строим и в
каком порядке). Решения с вариантами — `docs/architecture/adr/`.

## Правила параллельной работы (несколько сессий одновременно)

0. **`main` — ствол, ветки короткие.** Начинай раунд с `git fetch origin`
   и `git log --oneline origin/main -20`: соседние сессии могли поменять
   общие слои. Сообщения коммитов — прозой, с «почему».
1. **Одна задача = одна папка приложения.** Не трогай чужие `apps/*`.
2. **Общие слои меняются отдельно.** `packages/shared` и
   `supabase/migrations` меняют только задачи, которые явно про это,
   отдельным небольшим PR, который вливается ДО зависящих задач. Нужен
   новый тип или таблица, а задача не про контракты — остановись и скажи
   владельцу.
3. **Миграции — только добавление.** Новый файл
   `supabase/migrations/<YYYYMMDDHHMMSS>_<название>.sql`; применённые
   файлы не редактируются никогда. Новое значение enum — отдельным
   файлом из одной строки (каждый файл — своя транзакция).
4. **Не переименовывай и не перемещай** общие файлы без явного запроса.
5. **Решение шире своей папки пишется в файл** — в `CLAUDE.md` нужного
   уровня или в ADR — тем же коммитом, что и код. Сказанное в чате для
   других сессий не существует.
6. **Изоляцию проверяет исполняемый тест**: `bash supabase/tests/run.sh`.
   Меняешь политику или контракт прав — обновляй матрицу в
   `supabase/tests/01-core-rls.sql` тем же коммитом.
7. **Минуты CI платные**: новая проверка — ШАГ в задаче «Быстрые
   проверки», а не отдельная задача. CI идёт только на PR и только по
   затронутому (`scripts/ci-affected.sh`); полный прогон — раз в неделю.
8. **Бюджет размера правил**: корневой `CLAUDE.md` ≤ 40 КБ, `CLAUDE.md`
   приложения ≤ 60 КБ. Тема, переросшая абзац, уезжает в
   `docs/patterns/<тема>.md`, здесь остаётся одна строка со ссылкой.
   Проверяет `scripts/check-doc-size.mjs`.

## Архитектурные инварианты (не нарушать)

- **Один Postgres (Supabase на своём сервере), мультитенантность через
  RLS.** Иерархия `orgs → clubs`, членства `org_members` и
  `club_members`. Изоляция живёт в политиках базы, а не в коде
  приложений. Новая таблица получает `org_id` (и `club_id`, где
  уместно), каскадные внешние ключи, индексы и RLS в той же миграции.
- **Политика пишется по операциям, а не `for all`.** У DELETE нет
  `with check`: шаблон `using(читать) + with check(писать)` разрешает
  удалять тому, кто может читать. Четыре политики: select по
  `has_*_access`, insert/update/delete по `can_manage_*`.
- **Личность сотрудника в базе — `app.staff_id()`**, а не `auth.uid()`:
  она пуста без второго фактора (`aal2`) и у заблокированной учётки.
  Политика через `auth.uid()` — ошибка, тест её ловит. Функции записи
  никогда не возвращают `null` (`coalesce(…, false)`).
- **Update от имени рядового пользователя стережёт триггер
  `app.only_columns('<колонки>')`**, а не `with check`: тот видит только
  новую строку. В `with check` сверяется сеть/клуб ЦЕЛИ ссылки.
- **У каждого мира доступа своё пространство имён клеймов**: сотрудники
  — `sub`/`aal`, клиенты — `cl_client_id`/`cl_org_id`. Клейм одного мира
  никогда не называется как в другом (ADR platform-001).
- **`request.jwt.claims` читается только через `auth.jwt()`** (внутри —
  `nullif(…, '')`): прямое приведение `::jsonb` падает на пуле соединений.
- **`service_role` — только в модулях из закрытого списка** ADR
  platform-001 (вход и приглашения, воркер, загрузки, интеграции,
  аналитика по расписанию). Расширение списка — правкой ADR.
  `scripts/check-service-role.mjs` проверяет.
- **Условие политики с подзапросом к невидимой таблице — в
  security-definer-функцию**; stable-функции в политике — в скобках
  `(select app.f())`.
- **Список строк сортируется до однозначного порядка**: хвост цепочки —
  `id`. Списки листаются курсором, точное «сколько всего» не считается.
  PostgREST режет ответ до 1 000 строк без признака — `loadPaged`.
- **Все бакеты Storage приватные.** Загрузка — из браузера по
  подписанному URL, путь выбирает сервер; чтение — подписанной ссылкой
  после RLS-проверки строки-носителя; удаляя строку с файлом, удаляй
  файл (реестр `files`). SVG отклоняется.
- **Запись, которая обязана получиться, идёт через `mustWrite`**: отказ
  называет класс причины (`forbidden`/`duplicate`/`check`/`schema`/`fail`),
  `details` наружу не выносится. Действие, остающееся на странице,
  заканчивается `revalidatePath`, а не `redirect`.
- **Фоновая работа — только воркером через `jobs`** (`claim_jobs`,
  `for update skip locked`), никогда синхронно в запросе: письма, push,
  дайджесты, повторяющиеся задачи. Расписание — `pg_cron`.
- **Живые обновления — SSE + откат на опрос**, комната-снимок в процессе
  (ADR platform-003). WebSocket, Supabase Realtime, Redis — не вводить
  без нового ADR.
- **Уведомления: кому адресовано — решает база; доставка — воркер; лента
  в портале — источник правды**; push без персональных данных в теле
  (ADR platform-004).
- **Второй фактор — TOTP через GoTrue, обязателен для всех** (ADR
  platform-002). Маршруты подтверждения из писем сессию не выдают;
  ссылки собираются только из `PORTAL_PUBLIC_URL`.
- **Лимиты по IP и по учётке — в базе (`auth_rate_events`)**, не в
  памяти; `CLIENT_IP_HEADER` задаёт доверенный заголовок. Троттл, не
  вечная блокировка.
- **Заголовки безопасности (CSP, HSTS, Permissions-Policy) ставит
  middleware из переменных окружения**; `NEXT_PUBLIC_*` не используется
  — образ один на любое окружение, браузеру всё отдаёт сервер.
- **Никаких адресов, ключей и доменов в коде** — только переменные
  окружения. Новая переменная — запись в Coolify той же задачей.
- **Шрифты лежат в репозитории**, `next/font/google` не используется.
- **Имя продукта снаружи и имя в коде — разные вещи.** Подписи
  переименовываются свободно; папки, таблицы, типы, клеймы — никогда без
  явного запроса. Англицизмы в интерфейсе («таск», «мессенджер», «чекин»)
  не используются: «задача», «чаты», «регистрация».
- **ИИ ходит через поставщика Яндекс** (`lib/ai/`); API Anthropic из
  России не открывается, API Сбера требует сертификатов НУЦ.

## Миграции и выкат

**Миграции применяются сами при выкате. Руками их не применяют.**
Push в `main` → Coolify собирает образ → новый контейнер `portal` с
`MIGRATE_ON_START=1` запускает `supabase/apply.sh` (журнал
`app.schema_migrations`, контрольные суммы, advisory lock) → стартует →
проходит healthcheck → заменяет старый. Упавшая миграция оставляет
старый контейнер; чинится **новой** миграцией.

Ручное применение вредно: без строки в журнале следующий выкат падает
на «relation already exists» и останавливает все выкаты. Единственное
исключение — **разрушающие миграции** (`drop table/column`, `truncate`):
скрипт их не пропускает (`ALLOW_DESTRUCTIVE=1`), их применяет человек в
тихое время с бэкапом и отмечает в журнале.

**Миграция едет тем же PR, что и код, который на неё опирается.**
Читающая сторона рассинхрон переживает, пишущая — нет (`PGRST204`
роняет всю форму вместе с набранным текстом).

## Команды

```bash
pnpm install                    # из корня; pnpm workspaces
pnpm --filter portal dev        # портал, порт 3000 (apps/portal/.env.local)
pnpm --filter portal build      # прод-сборка с проверкой типов — гоняй перед PR
bash supabase/tests/run.sh      # одноразовый Postgres, все миграции, матрица RLS
node scripts/check-db-contract.mjs   # код ↔ схема (гоняется внутри run.sh)
```

## Деплой и готовность

Push в `main` → Coolify на Timeweb выкатывает затронутые приложения
(Watch Paths). **Готовую задачу заливай сам, не спрашивая разрешения**
(решение владельца Eventbase 16.08.2026, подтверждено для этой
платформы). Готова = сборка затронутого проходит, CI на PR зелёный.
Сомнение по сути задачи задаётся ДО работы: разрешение на выкат — не
разрешение угадывать.

В описании PR — имя файла миграции и что меняется в схеме; применять её
никому не нужно.
